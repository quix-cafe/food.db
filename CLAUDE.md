# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

food.db, a kitchen cost & recipe manager built from `spec.md` (the product spec; read it for intent). npm workspaces: `shared/` (costing math), `server/` (Express 5 + PostgreSQL), `client/` (React 19 + Vite SPA).

## Commands

```bash
npm install
npm run db:up            # Postgres 17 in Docker (also creates kitchen_test)
cp .env.example .env     # DATABASE_URL, TEST_DATABASE_URL, UPLOAD_DIR, PRICE_HIKE_THRESHOLD
npm run seed             # sample data; no-op if ingredients exist
npm run dev              # API :3000 (node --watch) + Vite :5173 (proxies /api)
npm test                 # shared unit tests + server integration tests
npm run build            # client → client/dist, served by the API in production
docker compose up -d --build   # full stack on :3000
npm run build:binary     # standalone executables → dist/*.tar.xz (needs Bun and xz; `-- linux-x64` for one target)
```

Single test file / test: `node --test shared/test/calc.test.js`, or from `server/`: `node --env-file=../.env --test --test-name-pattern="event summary" test/api.test.js`. The server integration tests **drop and recreate the `public` schema of `TEST_DATABASE_URL`**; they skip if it is unset. `TEST_DATABASE_URL=pglite://memory npm test -w server` runs the same suite on the embedded PGlite database the binary uses. Migrations (`server/migrations/*.sql`, applied in filename order, tracked in `schema_migrations`) run automatically on server start, or via `npm run migrate`. `001_schema.sql` is the whole schema (every migration so far is folded into it); add schema changes as new numbered files. Version 3 folded every earlier migration into 001, so backups and databases from before it aren't supported. Don't fold again: a backup listing a folded migration would be refused, and a database already past 001 would never get the folded changes.

## Deployment

Two ways to ship: Docker Compose (Postgres 17 container) or the standalone binary. **Standalone binary** (`scripts/build-binary.js`, entry `server/src/standalone.js`): `bun build --compile` cross-compiles one executable per target (linux/darwin × x64/arm64) holding the API, the built UI, the migrations and PGlite (Postgres 18 compiled to WASM, plus `pg_trgm`). The script generates `server/src/embedded.gen.js` (gitignored), which imports those files `with { type: 'file' | 'text' }`; `standalone.js` puts them on `globalThis.__FOODDB_EMBEDDED` before loading the rest, and `embedded.js` exposes them to `db.js` (PGlite runtime), `migrate.js` and `app.js` (UI). Bun's embedded files can be read but not streamed, so `db.js` copies the `pg_trgm` bundle to a temp file at startup. Module-level "run me directly" checks (`process.argv[1] === fileURLToPath(import.meta.url)`) are true for every module in the binary, so guard them with `!embedded`. The binary listens on 127.0.0.1 and keeps data in `~/Library/Application Support/food.db` or `$XDG_DATA_HOME/food.db` (`db/`, `uploads/`, `backups/`). Most of each executable is Bun's runtime (~80 MB); xz -9e packing roughly thirds it. Pushing a `v<version>` tag (must match `package.json`) runs `.github/workflows/release.yml`, which tests on PGlite, builds every target and publishes a GitHub Release.

**Two databases, one interface.** `DATABASE_URL` is a Postgres URL or `pglite://<dir>` (`pglite://memory` for a throwaway one). `db.js` wraps PGlite in the `pg.Pool` interface the routes use (`query`, `connect`, `tx`, `rowCount`), using pg's own type parsers, so both return identical JSON. PGlite is a single connection: `tx()` holds it exclusively, and module-level `query()` calls made inside a transaction run on it (AsyncLocalStorage) rather than deadlocking. Postgres 18 reports `ON DELETE RESTRICT` violations as `23001`, not `23503`; test with `fkViolation()` from `db.js`.

The image's `HEALTHCHECK` hits `/api/health`, which also runs `SELECT 1`. The pool has an `error` handler, so a database restart drops idle connections instead of crashing the app.

## Architecture

- **One costing engine.** `shared/src/calc.js` (`calculateRecipe`, `summarizeEvent`, `completePurchaseCosts`, …) is imported by both the API and the browser. The recipe builder's instant "Expected servings" scaling runs it client-side with no request; the API runs the same code for `/recipes/calculate`, the gallery and event summaries. Change formulas there only.
- **Money is never a float.** All math uses `decimal.js` (the `Decimal` clone exported from shared). Postgres `numeric` comes back as strings (pg default) and API responses keep amounts as decimal strings; the client formats them via `client/src/format.js`. `pg` is configured to return `date` columns as `YYYY-MM-DD` strings (`server/src/db.js`).
- **Price history is append-only.** `ingredient_purchases` rows are never added out of order or removed by edits, but a purchase entered wrong can be corrected in place (`PATCH /api/ingredients/:id/purchases/:purchaseId`, the drawer's Purchases table): its pack size, vendor, packs, pack price or total. Packs × pack price and the total must agree (`completePurchaseCosts` refuses them more than a cent and rounding apart, everywhere a purchase is saved); new packs alone keep the total, which is what the receipt says was paid, and a new pack price or total works out the other; "current price" is always the latest purchase by `purchase_date, created_at` via the `LATEST_PURCHASE` lateral join in `server/src/sql.js`, averaged with the other lines of that purchase's receipt for the same ingredient (a *trip*: two packs of chicken at different weights are one price, not a price change). The average is one average pack (pack price and pack size averaged per pack bought, so per unit = spent ÷ bought), computed the same way by `combinePurchases` in `shared/src/calc.js`; `latestLines` says how many lines went into it. A purchase without a receipt is a trip of its own. Recipes store only an amount per ingredient, so their cost moves with new purchases. A recipe's menu price either follows its cost at `target_margin` or is set by hand (`recipes.target_price`). Typing a price in the costing ticket sets `targetPrice` (and `targetMargin` = (1 − cost per serving / price) × 100, 6 decimals, where the slider resumes); `calculateRecipe({ targetPrice })` then keeps that price whatever the cost and returns the margin it makes as `targetMargin` (below 0 once cost passes it) with `priceSet: true`. Moving the margin slider or "Follow the margin instead" clears it. The gallery shows a Price set badge. Price movement in an ingredient's history (`GET /api/ingredients/:id/history` returns `trips` alongside `purchases`) compares each trip's price per unit with the previous trip from any vendor; lines inside a trip carry no change of their own. The drawer's chart, average, vendors table and hike notice use trips, and its Purchases table shows a several-line trip as an averaged row with its lines under it.
- **Units of measure.** Each ingredient has one `uom` (lb, oz, each…). Each purchase stores `quantity` (packs bought), `pack_size` (in that UOM) and `unit_cost` (the price of one pack), so price per unit = `unit_cost / pack_size`. A recipe line stores `amount` in the UOM, or in its own kitchen `unit` (`recipe_ingredients.unit`, null: the UOM; rice bought by the lb, used by the cup): `lineAmountInUom` (shared) converts it, weight↔volume through `ingredients.cup_grams` ("1 cup weighs" in the drawer; blank: `estimatedCupGrams` by name, rice 185 g), and `recipeUnits` lists what the builder's unit picker offers. `calculateRecipe` costs the converted amount; its `scaledAmount` is in the UOM (shopping list), `scaledLineAmount` in the line's unit, and an unconvertible line costs 0 with `unitProblem`. Saving refuses a unit that can't convert; a merge keeps a line's unit when the kept ingredient can take it. The builder and API accept fractions ("1 1/2", "½") via `parseAmount`, and save decimals. A purchase can't change an existing ingredient's UOM (400); new ingredients take the row's. Units are stored one way (`canonicalUom` in shared: "Lbs" → "lb", ea/ct/pc → "each", anything else lowercased), on create, rename and purchase.
- **Receipts come in as JSON.** Extraction happens outside the app (e.g. qwen). `POST /api/ingredients/import-receipt` normalises whatever key names the extractor used (`server/src/services/receipt.js`: a line's unit may be `unit_of_measure`, and its total `total_amount`; a multi-buy's "FOR" is no unit; a coupon may be only a negative unit price) and saves nothing. The receipt's `time` ('HH:MM', from a `time` key or a time written with the date; `receiptTime`) isn't stored apart from the source JSON: `GET /api/receipts` and `/:id` read it from there, and the Purchases list shows it with the date. A vendor printed in capitals is tidied on import ("H MART" → "H Mart"), and every place a vendor is saved (`vendorSpelling` in `server/src/matching.js`: receipts, purchases, a purchase's correction, and the import itself) takes the spelling already saved for that store, ignoring capitals and spacing, so one store isn't listed twice. It also returns `alreadyImported`: receipts from the same store and day with mostly the same lines, which the review shows with a link, since importing one twice doubles its purchases. Each line returns `match` (auto-resolved through a saved alias in `ingredient_aliases`, else an exact name) or `candidates`: up to five ingredients it might be, from the words it shares with their names or saved receipt names (`wordMatches` in `shared/src/names.js`: stemmed words, pack sizes and filler like "org" dropped, a cut-short receipt word matching the word it begins), then the closest `pg_trgm` name; `suggestion` is the first. The matching words have receipt shorthand spelled out (SWT → sweet, YELL → yellow), other names for one thing made one (green onion = scallion, dahi = yogurt, golgappa = pani puri, chick peas = chickpea), where it's from and brands seen on receipts dropped (USA, MEX, loose; Shan, Hunt's, Pepperidge Farm, store codes like EE and WC: `RECEIPT_FILLER`, `BRAND_PHRASES`) and a color alone never counting; a whole word beats a cut-short one. A candidate is `strong` when every word of its name is on the receipt, those are at least half the receipt's words, and nothing else does as well: the review starts that row on it, badged "Suggested match" with "Not this" (`toRow` in `ReviewLines.jsx`). Any other line with candidates can't be ticked until one is picked or "Add as new" is chosen, which uses a tidier name than the receipt's (`receiptName` in shared: capitals tidied, shorthand spelled out, known brands dropped, a size in the name such as "14oz" or "4P" taken as the pack size and unit), the receipt's wording kept as its receipt name. A line with no candidates starts on that name. In the grid the receipt's total is what was paid: changing packs keeps it and the pack price follows, changing the pack price or total works out the other. A line sold by weight saved to an ingredient in another weight unit gets its pack size converted (1 lb = 16 oz); to one counted another way (Onion Red, each) the row warns that the pack size must say how many make one lb. A generic alias (`server/src/matching.js`) is never applied automatically: one store prints "Grocery" on every line. A receipt name that says nothing at all (`isGenericName`: "GROCERY", "Grocery item", "MEAT", no word left once filler is dropped) is never saved as an alias, kept by a rename or merge, or resolved through an old one. This covers an alias that one receipt saved as two or more ingredients, and a name on several lines of the receipt being imported. Such a line gets `choices` (what it was saved as before, most often first) and `ambiguous` ('history' or 'receipt'); a kept row is sent with `skipAlias` so saving matches what the review showed. In the Review & Confirm grid (`ReceiptReviewPage` + `ReceiptNameCell`), the receipt's wording is never overwritten. Clicking the name opens an inline combobox to type a new name or pick an existing ingredient. Enter or blur commits, Escape cancels, and "Undo rename" reverts. Only rows ticked to save are committed, via `POST /api/ingredients/purchase`. It resolves by id, then alias, then exact name, creates any missing ingredient, and stores `alias` (the receipt wording) when it differs from the chosen ingredient's name. An existing alias is re-pointed to the new choice. A capitalization-only fix is a rename too: the row is sent with the ingredient's id plus the recased `name`, and the server renames that ingredient (a bare name only ever resolves, never renames). Renaming a row ticks it for saving. Once every line of a receipt is saved, the review page is replaced by a "Receipt saved" summary (`ReceiptSaved`). It adds up all of that receipt's saves: each purchase comes back with `ingredientName`, `uom` and `receiptName` (the receipt line's printed wording when it differs), plus new ingredients, aliases and renames. It offers Back to Ingredients or Add another receipt (`/ingredients/review` with no state shows the import form). Aliases are listed and removable in the ingredient drawer, and `GET /api/ingredients?q=` matches them too. Renaming an ingredient (drawer `PATCH`, a review recase, or a merge) keeps the old name as an alias, even when only its capitals changed (`keepOldName`); aliases are unique ignoring case, so a spelling already saved in other capitals is kept as first saved, and an alias that now equals the name exactly is dropped.
- **Duplicates and merging**. `findDuplicates` (`shared/src/names.js`) suggests pairs that are one thing under two names. A pair qualifies when a saved alias matches the other's name, or the names match on `ingredientKey`: pack sizes like "16 ct", grade words in `DESCRIPTORS` ("granulated", "kosher") and where it's from (`RECEIPT_FILLER`: USA, MEX, loose) are dropped, plurals folded, receipt shorthand spelled out and other names for one thing made one (`SYNONYMS`), and the words sorted, so "TOMATO PLUM USA MEX" is "Plum Tomato"; product words ("ground", "pickled") are kept. A near spelling also qualifies (edit distance 1 from 5 letters, 2 from 10). So do names alike on the words that say what it is (3+ letters, no receipt filler): the same words once store codes fall away ("EE PEAS CARR" and "WC PEAS AND CARR"), one name being the other plus one word that isn't in `PRODUCT_WORDS` ("POTATOES IDAHO US" and "Potato", but not "Ground Chicken" and "Chicken"; cuts like thigh and leg count as product words), or one different word each after two alike, usually the brand ("Acme Ginger Paste" and "Zeta Ginger Paste"), unless it's a color. `preferredKeep` picks the survivor: a real unit over box/each, then a typed name over a receipt's capitals, then the more specific name (pack sizes and where it's from don't count), then more history. `GET /api/ingredients/duplicates` serves the pairs; "Not the same" (`POST …/duplicates/dismiss`) stores the pair in `ingredient_pair_dismissals` (smaller id first, cascades). `POST /api/ingredients/:id/merge { intoId, factor?, dryRun? }` (`server/src/merge.js`) runs in one `tx()`. It moves purchases (`pack_size × factor`), recipe lines (`amount × factor`; a recipe listing both gets one summed line), `event_amounts` (summed on conflict), blend items (kitchen units, unchanged) and aliases, then adds the merged name as an alias. The survivor is test data only if both were; a missing category is filled in. `factor` defaults to `unitRatio` (same unit, or weight↔weight / volume↔volume, never across them); without one, the merge is a 400 asking for it. `dryRun` rolls back after computing each affected recipe's cost per serving and price before/after, which `MergeModal` shows as the preview.
- **Receipts and images.** Saving the first lines from the review grid creates a `receipts` row (vendor, date, source JSON, photos) via `POST /api/receipts` (multipart). The server also normalises the source into `receipt_lines` (same order as the import's `items`). Each review row carries its index as `receiptLine`, and saving it sets that line's `purchase_id`. Unsaved lines come back as `pendingLines` on `GET /api/receipts/:id`, grayed on the receipt's page under Purchases (`/purchases/:id`) and savable later through the same `ReviewLinesTable`. Deleting a purchase un-saves its line. Purchases then carry `receipt_id`; deleting a receipt sets it to null and keeps the purchases. Image files live in `UPLOAD_DIR` (relative paths resolve from the repo root; default `data/uploads`; Docker volume `uploads`). The `images` table rows belong to exactly one recipe or receipt (CHECK constraint, cascade). All file I/O goes through `server/src/images.js`: formats are sniffed from file bytes (HEIC rejected), files are removed when their owner is deleted, and duplicating a recipe copies them. Position 0 is a recipe's cover. A photo can be turned a quarter turn (`POST /api/images/:id/rotate { direction: 'left' | 'right' }`, `rotatePhoto` in `server/src/compress.js`; the receipt page's gallery passes `onRotate`, which puts Rotate buttons under each thumbnail and in the viewer): JPEG and PNG only, rewritten under a new file name like compressing. Image URLs carry `?v=` from the file name, so a turned or compressed photo isn't served from the browser's cache-forever copy. Lists and galleries load `thumbUrl` (`GET /api/images/:id/thumb`, `server/src/thumbs.js`): a JPEG at most 640 px on its longest side, made on first request with jimp (pure JS, so the binary needs no native code), kept in `UPLOAD_DIR/thumbs/<filename>.jpg` and removed with its image; WebP or an undecodable file is served full size. The Backup page's Compress photos card (`server/src/compress.js`, `/api/images/compress`) resamples JPEG and PNG photos whose longest side is over a chosen size (1024–4096 px slider, with 2048 and 4096 marked with their estimated saving). `GET` lists every photo's bytes and header dimensions (`imageSize`, nothing decoded), and the page estimates bytes × (size ÷ longest side)². `POST { maxSide, ids }` (at most 10; the page sends 2 at a time for progress) writes each result under a new file name, updates `filename`/`size_bytes` and removes the old file and thumbnail, keeping the original if resampling wouldn't shrink it. `POST /api/images/compress/snapshot` saves a `before-compressing-photos-*` snapshot first (ticked by default). Thumbnails aren't backed up; restore prunes ones whose image is gone. On the client, `ImageGallery` handles thumbnails, the lightbox and cover controls. Receipt photos travel from the import form to the review page in memory (`receiptDraft.js`), not in router state.
- **Spice Lab** (`/spice-lab`, `/api/blends`). A blend's items are an ingredient or a typed name, with an amount (fractions accepted) in a kitchen unit. `shared/src/units.js` converts everything to grams (`BLEND_UOM`) for the pie chart (spoons and pinches via `SPICE_GRAMS_PER_TSP` = 2.5) and costs linked items by converting into the ingredient's UOM where possible. In recipes a blend line (`recipe_ingredients.blend_id`, exactly one of ingredient/blend) is filled in by `loadRecipes` via `blendAsLine` as an item in grams whose pack is one batch (`packSize` = batch grams, `packPrice` = batch cost), so costing and the event shopping list (batches to make) need no special cases. Sauces are `spice_blends` rows with `kind = 'sauce'` and a `container` (`SAUCE_CONTAINERS`: 1/4 qt to 1 gal); `calculateBlend(items, blend)` weighs their volumes like water (`SAUCE_GRAMS_PER_TSP`) and returns `uom` 'oz', `batchSize` = the container's oz (which `blendAsLine` uses instead of grams) and `servingOz`. A sauce's price per serving is `spice_blends.sale_price` (`salePrice`, set in its editor; blank: its cost at the default margin). A sauce's serving is a size in oz (`spice_blends.serving_oz`); the server stores `servings` as the whole servings one container holds, and a sauce saved without one takes container ÷ servings. A sauce's amounts are for one container, and picking another container scales every amount to fill it; its editor's "Quarts to make" slider (¼ to 4 qt, more can be typed) only scales the view, with Scaled amount, Scaled g and Scaled cost columns, and resets when the container changes. A sauce stays a sauce, but a saved spice blend can become one: the editor's "Make it a sauce" switches the form to a container and serving size ("Keep it a spice blend" undoes it before saving), and `PUT /api/blends/:id { kind: 'sauce', container, … }` converts it, refused (409, naming them) while a recipe uses it, since recipes measure a blend in g and a sauce in oz. Quick add and the Spice Lab call a blend a Spice Blend. `bunch` converts to grams at about 75 g and `clove` at 7 g (pie and cost, never in `unitRatio`; `unitsForName` offers cloves only on fresh garlic), and an item linked to an ingredient may use that ingredient's own unit ("box"), which costs 1:1. `ingredients.unit_grams` (a unit's weight, for units kitchen measures can't reach; the API accepts it as `unitGrams`, but the drawer no longer edits it) lets `itemAmounts` (shared) convert spoons and ounces into such a unit and back; unset, one is taken as `estimatedUnitGrams` (a box 750 g, a chili 2 g, any other unit 75 g like a bunch). The Spice Lab and the event shopping list both use it. `spice_blends.servings` is what one batch makes; for a blend, the editor's "Servings needed" slider only scales the view (Scaled amount and cost columns), like the recipe calculator's "Scale to servings". The editor's table follows the recipe builder's: a linked item's name opens the `IngredientDrawer` (`components/IngredientDrawer.jsx`, shared with the Ingredients page and recipe builder; closing it refreshes the item's price), with its latest vendor and purchase date under it (`priceDate` from `loadBlends`), then unit price, pack size, store price, amount and unit, grams, share and total cost.
- **Recipe header.** Recipe name, Unit of measurement (`yield_unit`), Size per serving, Expected servings (`base_servings`, what the recipe makes as written) and Total qty needed. Only `total_yield` is stored: the builder derives size per serving = total yield ÷ servings on load, and editing either size or servings sets total yield = size × servings. Changing the size also scales every amount (`scaleAmounts`, from the amounts when the box was entered), so cost per serving follows; changing servings doesn't, as it says what the same batch makes. Saving bumps `recipes.updated_at`, shown on the gallery's cards. The Cost Calculator's "Scale to servings" is the separate what-if scaling (`expectedServings` in `calculateRecipe`).
- **Backup/restore** (`server/src/backup.js`, `/backup` page). A `.tar.gz` holds `backup.json` (every table in `TABLES`, plus the applied migrations) and `uploads/<file>`. When you add a table, add it to `TABLES` in FK insert order. `POST /api/events/:id/duplicate { name?, date? }` copies an event's plan (guests, vendor fee, recipes and sauces with pricing, `event_amounts`), not its results, notes or sales; the events list and the event page's footer offer it (`DuplicateEventModal` in `EventsPage.jsx`). Restore runs in two steps: `POST /api/backup/inspect` unpacks to a temp dir and returns a token, then `POST /api/backup/restore`. Restore first writes a snapshot to `BACKUP_DIR`, then in one transaction TRUNCATEs and reinserts via `jsonb_populate_recordset`, using only the tables and columns present in the backup, so a backup from an older version gets defaults for what it lacks (keep this working: a backup made today must restore in every later build). A backup listing a migration this build doesn't have is refused. Never fold a migration into 001 once a backup may list it. Timestamps are read as text so microseconds survive.
- **Test data**. `ingredients`, `ingredient_purchases`, `receipts`, `recipes`, `events` and `spice_blends` have `is_test`, whose default reads the transaction setting `app.test_data`. The client's test mode (per browser, `setTestMode` in `api.js`, striped bar in the shell) sends `X-Test-Data: 1`; `app.js` then runs the request in `runAsTestData` (`db.js`), which puts every query in a transaction that sets `app.test_data`, so no INSERT mentions the column. multer callbacks lose that async context, so `uploadImages` re-enters it. Backup and `/api/test-data` routes ignore the header. `server/src/testdata.js` clears test rows in dependency order, keeping any that real data still uses (a real recipe's test ingredient, a test recipe in a real event); `GET /api/test-data` is the same delete in a rolled-back transaction, as a preview. Clearing saves a `before-clearing-test-data-*` snapshot first.
- **Formulas** (spec §7): line cost = (pack price / pack size) × amount; scale = expected/base servings; price = cost per serving / (1 − margin/100), rounded to cents, default margin 75 (`DEFAULT_MARGIN`). Event shopping list groups by ingredient: `amount` = Σ amount × scale (in the UOM) `packsToBuy` = ceil(amount / latest pack size), `purchaseCost` = packs × pack price, `usedCost` = Σ line costs, and `leftover` = packs × pack size − amount. Labor isn't an ingredient: each event has its own `labor_hours` and `labor_rate` (per hour; a new event starts at the newest event's rate, a copy keeps both), saved from Financials through `PUT /api/events/:id/labor { hours?, rate? }`, apart from the plan's versioned save. `summarizeEvent(…, { labor: { hours, rate } })` adds hours × rate to `totalCost` and returns `labor: { hours, rate, cost }`. Financials always ends with the labor row: hours (`LaborInput`, "hrs") in the Servings column and "× $rate/hr" in Cost / serving, both editable, so it doesn't widen the table, and the Cost column adds up to `totalCost`. The list prints on its own: `printShoppingList` (`components/EventTabs.jsx`, which holds the event page's Financials, Shopping list and Results tabs) adds `body.printing`, and print CSS shows only `.print-target`, where the screen table is `.no-print` and `PrintedList` (a dense table grouped by category, tick boxes) is `.print-only`. Hide elements in print with classes, not inline `display`, which beats the print rules. Each shopping line carries its latest `vendor` and `priceDate`, shown in its own Bought column (under the name on a phone); every column sorts by a click on its header (`SHOP_COLUMNS`, name order by default, blanks last), and an ingredient's name opens the `IngredientDrawer`. Packs to buy can be typed over per ingredient for the chef's stock on hand or a spare (`PacksInput`, saved on leaving the box; blank or Reset clears it): `event_packs` (per event, copied with the event, never in the ingredient history), `PUT`/`DELETE /api/events/:id/packs/:ingredientId { packs }` answering with the summary, and `summarizeEvent(…, { packs })`, which makes it the line's `packsToBuy` (`packsSet`, `calculatedPacks`) so `purchaseCost` and `leftover` follow (below 0 shows as "from stock"), never the food cost. An edited line has a wash with a bar and box (`--edit-wash`/`--edit-line`: saffron, blue in the dark theme), with the calculated packs and Reset under it; under Total cost, the calculated total and what edits changed it by (`packsAdjustment`). The printed list puts lines zeroed out by hand under Inventory, last, and leaves plain water off (`TAP_WATER`: "Water", "cold water", not coconut water). Blend batches can't be set. A merged-away ingredient's set packs go with it.
- **Event types** (`events.kind`, `EVENT_KINDS` in shared; a Market / Personal Cheffing / Supper Club dropdown in the event page's top bar, a badge on the events list). A `market` (the default) sells each recipe by the serving, as below. A `personal_chef` job is a flat rate (`events.flat_price`) plus the groceries at cost. A `supper_club` sells tickets (`guest_count`, labelled Tickets) at a plate price (`flat_price`) for a plate of everything; Hoamsy takes its fee (`events.hoamsy_percent`, set in the top bar; null: `HOAMSY_FEE_PERCENT`, 25) off the tickets first, so revenue is only what's left (`flat.gross` is the ticket money, `hoamsyFee` the cut, not deducted again from profit; on Results the actual revenue is ticket money and the comparison uses it after the cut). Neither has per-recipe sale prices or deals (the planner swaps those columns for Revenue / serving, the summary's `netPrice`, and its margin, which update once the plan saves; stored prices are kept for switching back): `summarizeEvent(…, { format: { kind, flatPrice, tickets, hoamsyPercent } })` passes labor and the vendor fee through at cost (`flat.passThrough`: paid out first; Financials shows their rows with that as revenue and no profit), then shares what's left of the rate (the tickets after the cut; for a personal chef job, plus the groceries billed, amounts set by hand included) out by each item's share of the food cost as its revenue. Each item's margin per serving is that less its food and its share of amounts set by hand, a margin on food like a market recipe's (75% at the "75% on food" price), while the event's margin includes labor and fees; its `profit` is revenue less its own food, so the Financials columns add up. `flat.suggestedPrice` is the plate price or rate that sells the food (plus amounts set by hand) at `DEFAULT_MARGIN`, as a recipe's price does, and covers labor and the vendor fee at cost, so each fixed cost adds its own amount (over the tickets after Hoamsy's cut), not a marked-up one; it's offered under its box ("75% on food: $X") with Use. The summary's `grossMarginPercent` is the food's margin: revenue less the food (amounts set by hand included) over revenue, where at these events the revenue is what's left once labor and the vendor fee are paid back, so it's 75% at that price; `marginPercent` is the net margin, profit over all the revenue. The top bar and Financials show both, as Gross margin and Net margin. Financials adds a Margin / serving column at these events, and its Total row gives a plate (one serving of every item): its cost, revenue and margin per serving summed. Servings are still typed per recipe. Vendor fee, labor and the POS stay. These events are paid for up front, so the POS only places orders: the dishes (the summary gives them no price) show no prices, the ticket has one Order button (`payment_method = 'free'`) instead of the payment buttons, and the stats bar and board cards drop what was taken; the server refuses any other payment method there. There's no ticket or service item. Results' Recorded sales counts the free orders as served, with no possible revenue. `kind`, `flatPrice` and `hoamsyPercent` are saved with the plan, only when present in the body; a copy keeps them. The top bar (`.event-bar`, a CSS container, so its layout follows the panel's width) has fields sized to their values in two groups, name, date and type, then guests or tickets, price, Hoamsy % and vendor fee: one line from 1080px (a grid with fixed columns, the money fields at their max-content width, since Firefox gives a flex row of them a near-zero minimum and overlapped them), two rows below, a two-column grid under 560px. Under them `BarFigures` shows the summary's tickets, Hoamsy fee, revenue, cost, vendor fee, profit, gross margin and net margin in one even line (a 3-column grid under 600px, the last figure filling its row), dimmed while a change saves. The Financials tab's figures follow the same order.
- **Event pricing**. `event_recipes` has `sale_price` (null: the recipe's own target price), and an optional deal: `deal_qty` servings for `deal_price` ("3 for $15", both or neither). `eventPricing` in `shared/src/calc.js` works out the price, net price, margin per serving and revenue. It assumes every serving sells on the deal, with floor(servings / qty) deals. A deal that isn't cheaper than its servings at their price doesn't count (the planner says so, `dealNote`). The last deal entered for a recipe is kept on `recipes.deal_qty`/`deal_price` (`rememberDeal`) and fills in when its checkbox is ticked. Unticking says what was there straight away (`PUT /api/recipes/:id/deal`), since the debounced autosave may never have sent it. `summarizeEvent` uses it, so revenue and profit include the deal. `PUT /api/events/:id` and `POST …/recipes` keep a recipe's pricing when the body leaves the fields out; a blank value clears it. `components/EventPricing.jsx` holds the inputs shared by the planner's recipe table and `AddToEventModal`, and computes margin per serving client-side as you type. In the planner, a sale price that differs from the recipe's also offers "Set new price", which makes it the recipe's own (`PUT /api/recipes/:id/price`: not below cost, and saves the margin it makes) or the sauce's (`PUT /api/blends/:id/price`). A recipe's isn't offered with a serving size set for the event, whose price needn't divide into a recipe price exactly. In the planner a recipe's deal is a checkbox (`DealToggle`) whose inputs show once ticked; unticking clears it from the event, not from the recipe's memory. `event_recipes.serving_size` (`servingSize`, in the recipe's yield unit; null: the recipe's own, total yield ÷ servings) is what one serving is at this event ("3 tacos"), kept when left out of a body like the rest of the pricing. `eventServing` (shared) gives the `ratio` of recipe servings per event serving, and the cost and default price per event serving; `summarizeEvent` scales the recipe to expected servings × ratio, so the shopping list follows, while `expectedServings`, `salePrice` and deals stay per event serving. Typing a size doesn't change the servings already typed (the planner shows the total, "72 tacos in all"). `menuItemName` adds the size to the name on the sale menu and on recorded order lines, "Chicken Taco (3 tacos)". Sauces keep their serving size in oz.
- **Sales during the event**. The event page's "Record sales" button opens the POS screen for that event (`/pos?event=id`; `?sales=1` on the event page goes there too, so a phone can bookmark it). Tap a menu tile to build a line (an item with a deal is split: the larger part adds one, the smaller adds the deal's quantity), then tap Cash / Card / Venmo / Cash App, or "Given away" (`payment_method = 'free'`, charged 0, no deal). A deal applies by itself as often as the quantity allows. `POST /api/events/:id/sales { paymentMethod, items: [{ recipeId, quantity }] }` re-prices on the server from the event's pricing via `saleItem` (shared). Each line is stored in `event_sales` / `event_sale_items` with the name, unit price, deals, discount and amount at the time, so later price changes and deleted recipes (`recipe_id` set null) don't rewrite history. `GET …/sales` returns the lines (newest first) and totals per recipe and per method; `DELETE …/sales/:saleId` undoes one. Each sale stores `fee`, charged to the customer on top of the items for Venmo and Cash App (`paymentFee`/`PAYMENT_FEES` in shared: 1.9% + $0.10 and 2.6% + $0.15 of the whole charge, so the charge is (amount + fixed) ÷ (1 − percent) rounded up to the cent and the sale nets its amount). Revenue is the items' amounts; totals add `fees` and `charged`, and the pay buttons show the charge before you tap. The "After the event" tab offers the recorded revenue for Actual revenue. The Sales tab (`SalesTable`) lists every line with totals and its ticket time (`orderTimes().total`, with the average in the footer); removing a line there asks first.
- **Orders and the POS screen** (`/pos`, `pages/PosPage.jsx`). An order is an `event_sales` row: same pricing, fees and items, plus `customer_name` and `note` (optional, editable any time; each item has a `note` too, "no onions"), `status` (`ORDER_STATUSES`: in_progress, completed, cancelled; there is no placed stage, an order goes straight to the kitchen) and `status_changed_at`. `POST …/sales` takes `customerName`, `note`, items' `note` and `status` (default `completed`, for a sale already handed over; the POS screen sends `in_progress`, so everything joins the queue); `PATCH …/sales/:saleId` changes name, note or status. `in_progress_at` and `completed_at` time it (created_at is placed): `orderTimes` (shared) gives making and total in seconds, counting up while in progress, and `orderTimingSummary` averages completed orders. Reopening (back to in progress) keeps the start and clears the end. A sale handed over on the spot has neither, so it isn't timed. Cancelled orders stay listed but `salesReport` leaves them out of every total (`totals.byStatus` counts them), so revenue, Results and the Sales tab agree; in-progress orders count, since payment is taken when the order is placed. `useOrderEvent` picks the event with `anticipateEvent` (shared) from the events list (`sauceCount`, `openOrders`, `lastOrderAt`): an event today always wins (of several, one with a menu, then the busiest), else one with open orders, else the next, else the latest, preferring events with a menu. `?event=id` (Record sales and the screen's event list set it) names the event outright; that pick is remembered for the day in localStorage, but a remembered event on another date gives way to one today. An event not dated today is flagged. The queue polls every 10 s so several phones stay in step. Placing an order with a blank name shows a warning (`CustomerNameField`) with "Place without a name", which ignores taps for 500 ms so a double tap on a pay button can't confirm it; the server still accepts a nameless order. The magenta POS button in the top bar (`PosButton`, `App.jsx`) and Record sales open it through `useOpenPos` (`hooks.js`) as a full-page modal (`PosFrame`): the page it opened from goes in the location's state as `background`, and `App` keeps rendering that page underneath (`<Routes location={background}>`, `inert`), so closing returns to it with its scroll and edits, and `useLeaveGuard` doesn't count opening as leaving. A refresh stays in the POS, since the state is in browser history, and switching events keeps it. Without `background` (a bookmark, `?sales=1`) the POS renders alone, with an Exit link to the event. Closing or leaving with items on the ticket asks first (`useLeaveGuard`, last registered, so it's the one consulted while the POS is open). Menu items carry a color (`recipeColors` in `palette.js`, set on `saleMenu` rows; the planner's chosen rows use the same call), shown as a left border via `.tiled` and `--tile` on the POS screen and the event's recipe table: in id order each item takes the free slot in `MENU_COLORS` furthest from those taken, so the colors spread evenly and don't change between screens, though changing the menu can change them; past 8 they are `OTHER`. It has menu tiles, the current ticket (`useSaleDraft`, `components/Sales.jsx`) and an In progress / Done board, where in-progress orders are boxed in magenta, matching the pill in the stats bar (`.pos-stage`); the ticket takes a note per line ("+ Note") and one for the order, and a board card's order note can be edited like its name; where the two share a screen, its Orders tab shows a red pill while any order is open, whichever tab is active, and the stats bar's pills open that tab.
- **Sauces on an event.** `event_blends` puts a sauce on the menu: `servings` sold by the serving (no deals), made in whole containers of `container` (null: the sauce's own), with an optional `sale_price` per serving. The event body's `sauces` replaces them when present (a sale price left out is kept). `sauceContainer(blend, container)` (shared) gives `servingsPerContainer` (container oz ÷ serving oz), the cost per serving (batch cost × serving oz ÷ batch oz) and the default price (the sauce's `salePrice`, else the default margin). `summarizeEvent(…, { sauces })` prices each like a recipe, costs the containers made (ceil(servings ÷ per container)), and returns `sauces` for Financials. Their ingredients join the shopping list (in each ingredient's UOM, "Used in" the sauce; typed or unconvertible items listed as written, unpriced), unlike a blend line inside a recipe, which stays "make N batches". Shopping lines carry a `key`. Sales take `{ blendId }` items (`event_sale_items.blend_id`), per serving. The planner lists sauces at the bottom of the Recipes table, where the Servings column picks how many containers of which size; servings follow (containers × servings per container) and aren't typed. An event that opens with something chosen hides the rest behind a full-width `.fold-bar`; a new one shows everything.
- **Saving an event's plan.** The planner's autosave sends the whole plan, so `events.version` guards it: `PUT /api/events/:id` must name the `version` its copy came from (`POST …/recipes` also moves it). If the event has moved on, or the page is so old it sends none, it answers 409 and changes nothing. The planner keeps one save in flight at a time (each names the version the last returned); on a 409 it shows a notice offering "Load the saved plan" or "Replace it with this window's plan". While on screen it re-reads the event every 15 s and on focus (`useWhileVisible`, `hooks.js`) and, with nothing unsaved, takes a newer version with a toast. The page wrapper keys the planner by event id, so pending edits can't go out under the next event's id. Separately, `useNewBuild` compares the `/assets/` script in a fresh `/` with the one this page loaded (every 60 s and on focus; off in dev) and `NewBuildBar` (`App.jsx`) then asks for a refresh, without reloading on its own, since a ticket may be half built.
- **Vendor fee**. `events.vendor_fee` is set at the top of the event page and saved only when present in the PUT body, like the results fields. `summarizeEvent(recipes, amounts, { vendorFee })` takes it off `profit` and `marginPercent`, not `totalCost`. Financials shows it first and as a row against profit, and the After-the-event profit deducts it too.
- **After the event**. Events store `actual_guests`, `actual_revenue`, `actual_cost` and `notes`; `PUT /api/events/:id` updates only the result fields present in the body (blank clears one). The Results tab compares them with the plan client-side; profit uses the projected cost until an actual spend is entered. Below that, a separate Recorded sales section (`RecordedSales`) shows what Record sales logged per menu item: servings sold out of servings made (with a size set for the event, also what those come to, "60 / 90 tacos"), given away, and revenue out of the possible (the Financials revenue). It's kept apart from the actual figures because unlogged sales are missing from it.
- **CSV exports** go through `sendCsv` in `server/src/csv.js` (UTF-8 BOM for Excel, CRLF, and text columns marked `{ text: true }` get a `'` before a leading `= + - @` so spreadsheets don't run them as formulas). Routes: `/api/export/ingredients.csv`, `/api/export/purchases.csv` (linked from the Backup page's Spreadsheets card), `/api/events/:id/shopping-list.csv`; the client links to them with `<a download>`.
- **Server conventions.** Routes validate input with helpers in `server/src/validate.js` (throw `HttpError`; the error middleware in `app.js` maps it, `CalcError` → 400). API JSON is camelCase via SQL aliases. Multi-statement writes use `tx()`.
- **Dashboard** (`/`, `pages/DashboardPage.jsx`, `GET /api/dashboard?today=`). The main view, reached by the food.db title with no menu entry: the next 5 upcoming events and the 10 most sold items, by the recipe's own servings (`event_sale_items.recipe_servings`, set when sold, so "3 tacos for $14" counts 3), figures linking to their pages, then a line chart by day of purchases on receipts and revenue (`DashboardChart`; an event's actual revenue, else its recorded sales, before payment fees). `today` is the browser's day. Test data counts only while in test mode (`req.testData`), except that test events always list as upcoming, and cancelled orders count for nothing. Sales are for events dated in the last 30 days, spending for purchases dated in them.
- **Who changed what** (`server/src/audit.js`, `/api/audit`, the Backup page). Triggers on every data table (in `001_schema.sql`) write each row change to `audit_log`, so no route has to remember to; when you add a table, add its trigger there too. `actor` comes from the transaction setting `app.actor`, set by the same request context as test mode (`runInContext`, `db.js`) on any request that isn't a read. `actorFor` gives each network a random character's name in `actors` on its first change: `networkOf` takes IPv6 by /64 and private IPv4 by /24, so a home network is one character whatever addresses its devices rotate through, while Tailscale's addresses (one shared IPv6 range across a tailnet) stay separate. `req.ip` honors `X-Forwarded-For` only from a local proxy (`isLocalProxy`: loopback or Docker's gateway), since Tailscale Funnel and Docker otherwise make every client look alike. `txid` groups a save's rows, and `listChanges` nets out the delete-and-insert a plan save does, so an unchanged save lists nothing. Restore switches the triggers off (`app.audit`) and logs one line; these two tables aren't in `TABLES`, so backups don't carry them and a restore leaves them alone. The Sales tab's time cell shows an order's history on hover (`?history=1`); the event page shows who last edited the plan under its footer and names them in its conflict notice (`lastEdit`: `lastEditedBy`, with `you` for the same address, on the event's GET and PUT), and who entered its newest order (`lastOrder`: `lastOrderBy`, kept apart since an order doesn't change the plan); Database changes can show only what was deleted (`?only=deleted`). Nothing else in the interface says who changed something, until that's asked for. **Any manual change to the live database must identify itself**, in one transaction: `BEGIN; SELECT set_config('app.actor', 'Claude', true); …; COMMIT;`. Without it the change is listed as "Direct database change".
- **Search and lists.** The Purchases list (`/purchases`) sorts by any column but Photos (newest receipt first, by date and time). The header search (`/api/search`) covers ingredients (name or alias), recipes, sauces, spice blends, events (name or notes) and purchases (receipt vendor). The Recipes page shows cards or a table (Grid / Table, remembered per browser as `recipesView`; the table sorts by any column, `RECIPE_COLUMNS`). `.shell` clips horizontal overflow (`overflow-x: clip`, which keeps sticky working), since the page itself never scrolls sideways. The Ingredients table's Purchases column counts packs bought (each line's quantity, a fractional, weighed one as 1; several lines on one receipt each count), and Used in (`useCount`) counts recipes using it (directly or through a blend) plus the blends and sauces holding it.
- **Client conventions.** `useApi(path)` fetches and refetches whenever `notifyDataChanged()` fires, which every mutation calls. The event planner autosaves (debounced PUT). Row reordering (recipe lines, blend spices) uses `useRowReorder` from `hooks.js`: pointer events on a handle (works on touch, unlike HTML5 drag and drop) plus arrow keys. The recipe builder and Spice Lab editor use `SaveButton` (`ui.jsx`): its labels share one grid cell so the width never changes, and on a phone, unsaved changes float a copy at the bottom once the header button scrolls away. `useStickyTableHeads` (`hooks.js`, run in `App`) keeps page tables' headers in view: a table that fits gets `data-fits="1"` and CSS sticky under the page bar (`--sticky-top`), a wider one has its header cells translated with the page scroll. Pages with unsaved edits (recipe builder, receipt review, a receipt's not-saved-yet lines) use `useLeaveGuard(dirty)` from `hooks.js` with `<LeaveModal>`; call `allowLeave()` before navigating away on purpose. It relies on the data router set up in `main.jsx`. Styling is plain CSS tokens in `client/src/styles.css`; use the tokens rather than literal colors, since `:root[data-theme='dark']` redefines them for the dark theme (screen only, so printing stays light). `ThemeToggle` in `App.jsx` (bottom of the sidebar; on phones in the top bar beside the menu button) is a sun/moon switch, light by default; it saves the choice as `theme` in localStorage, and an inline script in `index.html` applies it before the first paint. Archivo is bundled via `@fontsource-variable/archivo`. Phones (≤ 640px) get their own block at the end of it: `.hide-sm` / `.show-sm` swap what a phone shows (category chips for a dropdown, a tab's `short` label, columns of wide tables), page descriptions are hidden, and the event's recipe table (`.cards-sm`) becomes one short card per row, labelled from each cell's `data-label`. On the event page, switching tabs holds the tab area at its height until scrolling up no longer needs it, so a short or loading tab can't pull the scroll position away from the tab bar.

`tests/receipt*.json` are real extractor outputs used as fixtures by `server/test/receipt.test.js`. They cover the main receipt shapes: a sections map, `{section, entries}` groups, discount and "PRICE YOU PAY" lines, `"2 @ $2.99 ea"` quantities, nested totals, and (`receipt4.json`) `unit_of_measure`/`total_amount` keys with a multi-buy and a negative-price coupon. `receipt5.json`–`receipt7.json` are made up to stress ingredient matching against the kitchen's own ingredients (eggs and words beginning with egg, puff pastry with no units, tortillas with extra words, brands, Spanish names, other names for one thing, generic names); import them to see how the review treats each kind of line. When a new extractor format breaks the import, add its JSON there with a test.
