# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

food.db, a kitchen cost & recipe manager built from `spec.md` (the product spec; read it for intent). npm workspaces: `shared/` (costing math), `server/` (Express 5 + PostgreSQL), `client/` (React 19 + Vite SPA).

## Commands

```bash
npm install
npm run db:up            # Postgres 17 in Docker (also creates kitchen_test)
cp .env.example .env     # DATABASE_URL, TEST_DATABASE_URL, UPLOAD_DIR, PRICE_HIKE_THRESHOLD
npm run seed             # sample data; no-op if ingredients exist
npm run dev              # API :3000 (node --watch) + Vite :5173 (proxies /api)
npm test                 # shared unit tests + server integration tests
npm run build            # client → client/dist, served by the API in production
docker compose up -d --build   # full stack on :3000
npm run build:binary     # standalone executables → dist/*.tar.xz (needs Bun and xz; `-- linux-x64` for one target)
```

Single test file / test: `node --test shared/test/calc.test.js`, or from `server/`: `node --env-file=../.env --test --test-name-pattern="event summary" test/api.test.js`. The server integration tests **drop and recreate the `public` schema of `TEST_DATABASE_URL`**; they skip if it is unset. `TEST_DATABASE_URL=pglite://memory npm test -w server` runs the same suite on the embedded PGlite database the binary uses. Migrations (`server/migrations/*.sql`, applied in filename order, tracked in `schema_migrations`) run automatically on server start, or via `npm run migrate`. `001_schema.sql` is the whole schema: every earlier migration was combined into it, and databases or backups from before that aren't supported. Add schema changes as new numbered files.

## Deployment

Two ways to ship: Docker Compose (Postgres 17 container) or the standalone binary. **Standalone binary** (`scripts/build-binary.js`, entry `server/src/standalone.js`): `bun build --compile` cross-compiles one executable per target (linux/darwin × x64/arm64) holding the API, the built UI, the migrations and PGlite (Postgres 18 compiled to WASM, plus `pg_trgm`). The script generates `server/src/embedded.gen.js` (gitignored), which imports those files `with { type: 'file' | 'text' }`; `standalone.js` puts them on `globalThis.__FOODDB_EMBEDDED` before loading the rest, and `embedded.js` exposes them to `db.js` (PGlite runtime), `migrate.js` and `app.js` (UI). Bun's embedded files can be read but not streamed, so `db.js` copies the `pg_trgm` bundle to a temp file at startup. Module-level "run me directly" checks (`process.argv[1] === fileURLToPath(import.meta.url)`) are true for every module in the binary, so guard them with `!embedded`. The binary listens on 127.0.0.1 and keeps data in `~/Library/Application Support/food.db` or `$XDG_DATA_HOME/food.db` (`db/`, `uploads/`, `backups/`). Most of each executable is Bun's runtime (~80 MB); xz -9e packing roughly thirds it. Pushing a `v<version>` tag (must match `package.json`) runs `.github/workflows/release.yml`, which tests on PGlite, builds every target and publishes a GitHub Release.

**Two databases, one interface.** `DATABASE_URL` is a Postgres URL or `pglite://<dir>` (`pglite://memory` for a throwaway one). `db.js` wraps PGlite in the `pg.Pool` interface the routes use (`query`, `connect`, `tx`, `rowCount`), using pg's own type parsers, so both return identical JSON. PGlite is a single connection: `tx()` holds it exclusively, and module-level `query()` calls made inside a transaction run on it (AsyncLocalStorage) rather than deadlocking. Postgres 18 reports `ON DELETE RESTRICT` violations as `23001`, not `23503`; test with `fkViolation()` from `db.js`.

The image's `HEALTHCHECK` hits `/api/health`, which also runs `SELECT 1`. The pool has an `error` handler, so a database restart drops idle connections instead of crashing the app.

## Architecture

- **One costing engine.** `shared/src/calc.js` (`calculateRecipe`, `summarizeEvent`, `completePurchaseCosts`, …) is imported by both the API and the browser. The recipe builder's instant "Expected servings" scaling runs it client-side with no request; the API runs the same code for `/recipes/calculate`, the gallery and event summaries. Change formulas there only.
- **Money is never a float.** All math uses `decimal.js` (the `Decimal` clone exported from shared). Postgres `numeric` comes back as strings (pg default) and API responses keep amounts as decimal strings; the client formats them via `client/src/format.js`. `pg` is configured to return `date` columns as `YYYY-MM-DD` strings (`server/src/db.js`).
- **Price history is append-only.** `ingredient_purchases` rows are never updated, except that `pack_size` can be corrected (`PATCH /api/ingredients/:id/purchases/:purchaseId`); "current price" is always the latest purchase by `purchase_date, created_at` via the `LATEST_PURCHASE` lateral join in `server/src/sql.js`, averaged with the other lines of that purchase's receipt for the same ingredient (a *trip*: two packs of chicken at different weights are one price, not a price change). The average is one average pack (pack price and pack size averaged per pack bought, so per unit = spent ÷ bought), computed the same way by `combinePurchases` in `shared/src/calc.js`; `latestLines` says how many lines went into it. A purchase without a receipt is a trip of its own. Recipes store only an amount per ingredient, so their cost moves with new purchases. The costing ticket's target price and margin are two views of one stored value: typing a price sets `targetMargin` = (1 − cost per serving / price) × 100, kept to 6 decimals so the price reproduces to the cent. Price movement in an ingredient's history (`GET /api/ingredients/:id/history` returns `trips` alongside `purchases`) compares each trip's price per unit with the previous trip from any vendor; lines inside a trip carry no change of their own. The drawer's chart, average, vendors table and hike notice use trips, and its Purchases table shows a several-line trip as an averaged row with its lines under it.
- **Units of measure.** Each ingredient has one `uom` (lb, oz, each…). Each purchase stores `quantity` (packs bought), `pack_size` (in that UOM) and `unit_cost` (the price of one pack), so price per unit = `unit_cost / pack_size`. A recipe line stores `amount` in the UOM. A purchase can't change an existing ingredient's UOM (400); new ingredients take the row's.
- **Receipts come in as JSON.** Extraction happens outside the app (e.g. qwen). `POST /api/ingredients/import-receipt` normalises whatever key names the extractor used (`server/src/services/receipt.js`) and saves nothing. Each line returns `match` (auto-resolved through a saved alias in `ingredient_aliases`, else an exact name) or a `suggestion` (closest `pg_trgm` name, never applied automatically). A generic alias (`server/src/matching.js`) is never applied automatically: one store prints "Grocery" on every line. This covers an alias that one receipt saved as two or more ingredients, and a name on several lines of the receipt being imported. Such a line gets `choices` (what it was saved as before, most often first) and `ambiguous` ('history' or 'receipt'); a kept row is sent with `skipAlias` so saving matches what the review showed. In the Review & Confirm grid (`ReceiptReviewPage` + `ReceiptNameCell`), the receipt's wording is never overwritten. Clicking the name opens an inline combobox to type a new name or pick an existing ingredient. Enter or blur commits, Escape cancels, and "Undo rename" reverts. Only rows ticked to save are committed, via `POST /api/ingredients/purchase`. It resolves by id, then alias, then exact name, creates any missing ingredient, and stores `alias` (the receipt wording) when it differs from the chosen ingredient's name. An existing alias is re-pointed to the new choice. A capitalization-only fix is a rename too: the row is sent with the ingredient's id plus the recased `name`, and the server renames that ingredient (a bare name only ever resolves, never renames). Renaming a row ticks it for saving. Once every line of a receipt is saved, the review page is replaced by a "Receipt saved" summary (`ReceiptSaved`). It adds up all of that receipt's saves: each purchase comes back with `ingredientName`, `uom` and `receiptName` (the receipt line's printed wording when it differs), plus new ingredients, aliases and renames. It offers Back to Ingredients or Add another receipt (`/ingredients/review` with no state shows the import form). Aliases are listed and removable in the ingredient drawer, and `GET /api/ingredients?q=` matches them too. Renaming an ingredient (drawer `PATCH`, a review recase, or a merge) keeps the old name as an alias, even when only its capitals changed (`keepOldName`); aliases are unique ignoring case, so a spelling already saved in other capitals is kept as first saved, and an alias that now equals the name exactly is dropped.
- **Duplicates and merging**. `findDuplicates` (`shared/src/names.js`) suggests pairs that are one thing under two names. A pair qualifies when a saved alias matches the other's name, or the names match on `ingredientKey`: pack sizes like "16 ct" and grade words in `DESCRIPTORS` ("granulated", "kosher") are dropped and plurals folded, while product words ("ground", "pickled") are kept. A near spelling also qualifies (edit distance 1 from 5 letters, 2 from 10). `preferredKeep` picks the survivor: a real unit over box/each, then the more specific name (pack sizes don't count), then more history. `GET /api/ingredients/duplicates` serves the pairs; "Not the same" (`POST …/duplicates/dismiss`) stores the pair in `ingredient_pair_dismissals` (smaller id first, cascades). `POST /api/ingredients/:id/merge { intoId, factor?, dryRun? }` (`server/src/merge.js`) runs in one `tx()`. It moves purchases (`pack_size × factor`), recipe lines (`amount × factor`; a recipe listing both gets one summed line), `event_amounts` (summed on conflict), blend items (kitchen units, unchanged) and aliases, then adds the merged name as an alias. The survivor is test data only if both were; a missing category is filled in. `factor` defaults to `unitRatio` (same unit, or weight↔weight / volume↔volume, never across them); without one, the merge is a 400 asking for it. `dryRun` rolls back after computing each affected recipe's cost per serving and price before/after, which `MergeModal` shows as the preview. Labor never merges.
- **Receipts and images.** Saving the first lines from the review grid creates a `receipts` row (vendor, date, source JSON, photos) via `POST /api/receipts` (multipart). The server also normalises the source into `receipt_lines` (same order as the import's `items`). Each review row carries its index as `receiptLine`, and saving it sets that line's `purchase_id`. Unsaved lines come back as `pendingLines` on `GET /api/receipts/:id`, grayed on the receipt's page under Purchases (`/purchases/:id`) and savable later through the same `ReviewLinesTable`. Deleting a purchase un-saves its line. Purchases then carry `receipt_id`; deleting a receipt sets it to null and keeps the purchases. Image files live in `UPLOAD_DIR` (relative paths resolve from the repo root; default `data/uploads`; Docker volume `uploads`). The `images` table rows belong to exactly one recipe or receipt (CHECK constraint, cascade). All file I/O goes through `server/src/images.js`: formats are sniffed from file bytes (HEIC rejected), files are removed when their owner is deleted, and duplicating a recipe copies them. Position 0 is a recipe's cover. On the client, `ImageGallery` handles thumbnails, the lightbox and cover controls. Receipt photos travel from the import form to the review page in memory (`receiptDraft.js`), not in router state.
- **Spice Lab** (`/spice-lab`, `/api/blends`). A blend's items are an ingredient or a typed name, with an amount (fractions accepted) in a kitchen unit. `shared/src/units.js` converts everything to grams (`BLEND_UOM`) for the pie chart (spoons and pinches via `SPICE_GRAMS_PER_TSP` = 2.5) and costs linked items by converting into the ingredient's UOM where possible. In recipes a blend line (`recipe_ingredients.blend_id`, exactly one of ingredient/blend) is filled in by `loadRecipes` via `blendAsLine` as an item in grams whose pack is one batch (`packSize` = batch grams, `packPrice` = batch cost), so costing and the event shopping list (batches to make) need no special cases. Sauces are `spice_blends` rows with `kind = 'sauce'` and a `container` (`SAUCE_CONTAINERS`: 1/4 qt to 1 gal); `calculateBlend(items, blend)` weighs their volumes like water (`SAUCE_GRAMS_PER_TSP`) and returns `uom` 'oz' and `batchSize` = the container's oz, which `blendAsLine` uses instead of grams. Kind is fixed once created. `bunch` converts to grams at about 75 g (pie only, never in `unitRatio`), and an item linked to an ingredient may use that ingredient's own unit ("box"), which costs 1:1. `spice_blends.servings` is what one batch makes; the editor's "Servings needed" slider only scales the view (Scaled amount column), like the recipe calculator's "Scale to servings".
- **Recipe header.** Recipe name, Unit of measurement (`yield_unit`), Size per serving, Expected servings (`base_servings`, what the recipe makes as written) and Total qty needed. Only `total_yield` is stored: the builder derives size per serving = total yield ÷ servings on load, and editing either size or servings sets total yield = size × servings. The Cost Calculator's "Scale to servings" is the separate what-if scaling (`expectedServings` in `calculateRecipe`).
- **Backup/restore** (`server/src/backup.js`, `/backup` page). A `.tar.gz` holds `backup.json` (every table in `TABLES`, plus the applied migrations) and `uploads/<file>`. When you add a table, add it to `TABLES` in FK insert order. Restore runs in two steps: `POST /api/backup/inspect` unpacks to a temp dir and returns a token, then `POST /api/backup/restore`. Restore first writes a snapshot to `BACKUP_DIR`, then in one transaction TRUNCATEs and reinserts via `jsonb_populate_recordset`, using only the columns present in the backup so older backups get defaults. Backups listing a migration this build doesn't have are refused (including any from before the migrations were combined). Timestamps are read as text so microseconds survive.
- **Test data**. `ingredients`, `ingredient_purchases`, `receipts`, `recipes`, `events` and `spice_blends` have `is_test`, whose default reads the transaction setting `app.test_data`. The client's test mode (per browser, `setTestMode` in `api.js`, striped bar in the shell) sends `X-Test-Data: 1`; `app.js` then runs the request in `runAsTestData` (`db.js`), which puts every query in a transaction that sets `app.test_data`, so no INSERT mentions the column. multer callbacks lose that async context, so `uploadImages` re-enters it. Backup and `/api/test-data` routes ignore the header. `server/src/testdata.js` clears test rows in dependency order, keeping any that real data still uses (a real recipe's test ingredient, a test recipe in a real event); `GET /api/test-data` is the same delete in a rolled-back transaction, as a preview. Clearing saves a `before-clearing-test-data-*` snapshot first. Labor is never test data: the `labor_not_test` trigger forces `is_test = false` on Labor (`is_labor()`, same rule as `isLabor`) and its purchases. Lists return `isTest`; `<TestBadge>` shows it.
- **Formulas** (spec §7): line cost = (pack price / pack size) × amount; scale = expected/base servings; price = cost per serving / (1 − margin/100), rounded to cents, default margin 70. Event shopping list groups by ingredient: `amount` = Σ amount × scale (in the UOM) `packsToBuy` = ceil(amount / latest pack size), `purchaseCost` = packs × pack price, `usedCost` = Σ line costs, and `leftover` = packs × pack size − amount. Labor's "needed" is editable on the shopping list: `event_amounts` (`PUT/DELETE /api/events/:id/amounts/:ingredientId`) stores a per-event amount that replaces the scaled total, and the cost difference is returned as `adjustment` and folded into the event's `totalCost`/profit (per-recipe rows keep the recipes' own figures). The list prints on its own: `printShoppingList` in `EventPlanner` adds `body.printing`, and print CSS shows only `.print-target`, where the screen table is `.no-print` and `PrintedList` (a dense table grouped by category, tick boxes, no labor) is `.print-only`. Hide elements in print with classes, not inline `display`, which beats the print rules. Each shopping line carries its latest `vendor`.
- **Event pricing**. `event_recipes` has `sale_price` (null: the recipe's own target price), and an optional deal: `discount_amount` off every `discount_qty` servings (null qty: per serving). `eventPricing` in `shared/src/calc.js` works out the price, net price, margin per serving and revenue. It assumes every serving sells on the deal, with floor(servings / qty) deals. `summarizeEvent` uses it, so revenue and profit include the deal. `PUT /api/events/:id` and `POST …/recipes` keep a recipe's pricing when the body leaves the fields out; a blank value clears it. `components/EventPricing.jsx` holds the inputs shared by the planner's recipe table and `AddToEventModal`, and computes margin per serving client-side as you type.
- **Sales during the event**. The event page's "Record sales" button (or `?sales=1`, which a phone can bookmark) opens `SalesModal`. Use +/− per recipe to build a line, tick "Deal used" when the recipe's deal fits the quantity, then tap Cash / Card / Venmo / Cash App, or "Given away" (`payment_method = 'free'`, charged 0, no deal). `POST /api/events/:id/sales { paymentMethod, items: [{ recipeId, quantity, dealUsed }] }` re-prices on the server from the event's pricing via `saleItem` (shared). Each line is stored in `event_sales` / `event_sale_items` with the name, unit price, deals, discount and amount at the time, so later price changes and deleted recipes (`recipe_id` set null) don't rewrite history. `GET …/sales` returns the lines (newest first) and totals per recipe and per method; `DELETE …/sales/:saleId` undoes one. Each sale stores `fee`, charged to the customer on top of the items for Venmo and Cash App (`paymentFee`/`PAYMENT_FEES` in shared: 1.9% + $0.10 and 2.6% + $0.15 of the whole charge, so the charge is (amount + fixed) ÷ (1 − percent) rounded up to the cent and the sale nets its amount). Revenue is the items' amounts; totals add `fees` and `charged`, and the pay buttons show the charge before you tap. The "After the event" tab offers the recorded revenue for Actual revenue. The Sales tab (`SalesTable`) lists every line with totals; removing a line there asks first.
- **Sauces on an event.** `event_blends` puts a sauce on the menu: `servings` sold by the serving (no deals), made in whole containers of `container` (null: the sauce's own), with an optional `sale_price` per serving. The event body's `sauces` replaces them when present (a sale price left out is kept). `sauceContainer(blend, container)` (shared) gives `servingsPerContainer` (the sauce's servings × container oz ÷ batch oz), the cost per serving (batch cost ÷ servings) and the default price (default margin). `summarizeEvent(…, { sauces })` prices each like a recipe, costs the containers made (ceil(servings ÷ per container)), and returns `sauces` for Financials. Their ingredients join the shopping list (in each ingredient's UOM, "Used in" the sauce; typed or unconvertible items listed as written, unpriced), unlike a blend line inside a recipe, which stays "make N batches". Shopping lines carry a `key`. Sales take `{ blendId }` items (`event_sale_items.blend_id`), per serving. The planner lists sauces at the bottom of the Recipes table. An event that opens with something chosen hides the rest behind a full-width `.fold-bar`; a new one shows everything.
- **Vendor fee**. `events.vendor_fee` is set at the top of the event page and saved only when present in the PUT body, like the results fields. `summarizeEvent(recipes, amounts, { vendorFee })` takes it off `profit` and `marginPercent`, not `totalCost`. Financials shows it first and as a row against profit, and the After-the-event profit deducts it too.
- **After the event**. Events store `actual_guests`, `actual_revenue`, `actual_cost` and `notes`; `PUT /api/events/:id` updates only the result fields present in the body (blank clears one). The Results tab compares them with the plan client-side; profit uses the projected cost until an actual spend is entered.
- **CSV exports** go through `sendCsv` in `server/src/csv.js` (UTF-8 BOM for Excel, CRLF, and text columns marked `{ text: true }` get a `'` before a leading `= + - @` so spreadsheets don't run them as formulas). Routes: `/api/export/ingredients.csv`, `/api/export/purchases.csv`, `/api/events/:id/shopping-list.csv`; the client links to them with `<a download>`.
- **Server conventions.** Routes validate input with helpers in `server/src/validate.js` (throw `HttpError`; the error middleware in `app.js` maps it, `CalcError` → 400). API JSON is camelCase via SQL aliases. Multi-statement writes use `tx()`.
- **Client conventions.** `useApi(path)` fetches and refetches whenever `notifyDataChanged()` fires, which every mutation calls. The event planner autosaves (debounced PUT). Row reordering (recipe lines, blend spices) uses `useRowReorder` from `hooks.js`: pointer events on a handle (works on touch, unlike HTML5 drag and drop) plus arrow keys. Labor (`isLabor`) has no purchases UI: the ingredient drawer edits its rate, saved as a 1 × 1-unit price record so costing reads it like any latest price. Pages with unsaved edits (recipe builder, receipt review, a receipt's not-saved-yet lines) use `useLeaveGuard(dirty)` from `hooks.js` with `<LeaveModal>`; call `allowLeave()` before navigating away on purpose. It relies on the data router set up in `main.jsx`. Styling is plain CSS tokens in `client/src/styles.css`, with Archivo bundled via `@fontsource-variable/archivo`.

`tests/receipt*.json` are real extractor outputs used as fixtures by `server/test/receipt.test.js`. They cover the main receipt shapes: a sections map, `{section, entries}` groups, discount and "PRICE YOU PAY" lines, `"2 @ $2.99 ea"` quantities, and nested totals. When a new extractor format breaks the import, add its JSON there with a test.
